# {app_name} Authoritative Source Inventory & Authority Hierarchy

This index provides the verified inventory of all source materials available within the {app_name} environment, categorized according to the **Five-Level Source Authority Model**.

---

## 1. The Five-Level Source Authority Model

| Level | Classification | Scope & Permitted Usage | Constraints |
| :--- | :--- | :--- | :--- |
| **Level 1** | **Official Authoritative Policy** | DILG issuances, official PDMU Operations Manual, national guidelines, statutory annexes, executive issuances, and procurement acts (RA 9184, RA 12009, RA 11032, COA Circular 2012-001). Governs official deadlines, procedural sequences, formal notice issuance, and statutory compliance standards. | Primary source of truth. Cannot be overridden by operational preference or code defaults. |
| **Level 2** | **Verified Operational Practice** | Transcribed interviews and process walkthroughs with DILG Laguna PDMU personnel. Documents how personnel actually execute tasks, field realities, day-to-day intake, and inter-office transmittals. | Explains operational context. Must NOT be presented as formal policy unless corroborated by Level 1 sources. |
| **Level 3** | **Current System Implementation** | Current production backend and frontend code, registered AI tools, route guards, database models, and workflow services in {app_name}. | Answers "How does {app_name} currently do this?" Must NOT be conflated with official DILG regulations. |
| **Level 4** | **Internal Project Documentation** | Technical specifications, forensic audit reports, architectural decision records, and capstone documentation in `docs/research/`. | Supporting analytical context and reconciliation records. |
| **Level 5** | **General Model Knowledge** | Base LLM pre-training knowledge. | Subordinated. If an operational or DILG domain question is not supported by Levels 1–4, the assistant must state that the information cannot be verified. |
